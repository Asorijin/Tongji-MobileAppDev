## 2. 观察方法

1. **以普通用户身份操作**参考 App：拍照、导入、确认、保存、搜索、打标签、导出。
2. 对每个操作记录：入口 → 界面变化（可见控件、提示文案、状态）→ 结果（列表/数据/文件变化）→ 异常路径。
3. 只记录**外部可观察行为**，不猜测内部实现。
4. 每个观察到的行为都标注：
   - **已观察**：在锁定环境中亲手复现；
   - **规格假设**：合理推断但未逐项核对（需列入 §5 待核对项）；
   - **规格定义**：复刻环境无法观察或不适用（如模拟器无相机），由本项目的规格直接定义。

> 说明：本文件是「记录」不是「宣传」。凡是未经观察者实机核对的内容，一律归入 §5 待核对项，
> 不写成确定结论；本仓库的自动化测试与验收也不依赖这些未核对条目的字面文案。

### 3.3 「CamCard 究竟把一张名片变成了什么？」（Week 1 核心问题）

从外部行为看，一张名片进入系统后依次变成四层数据：

```text
① 图像     原始照片 → 校正后的名片图像（区域裁剪 + 透视/方向校正）
② 文本     OCR 原始文本（按行）——系统内部保留，用于复核
③ 字段     结构化联系人：姓名 / 公司 / 职位 / 部门 / 手机 / 办公电话 / 传真 / Email / 网址 / 地址 / 邮编 / 备注
④ 记录     可搜索、可打标签、可编辑、可导出、重启不丢的 BusinessCard 记录
```

复刻据此定义 `BusinessCard` Schema（`docs/data-model.md`）：四个层次在数据模型中**全部保留**，
其中 ②（原始文本）是概率性 AI 输出与可靠软件数据之间的「证据链」——这是本项目的关键设计。

## 4. 识别流程分析（外部行为）

```text
点击扫描
  → 选择拍摄 / 导入               （P3）
  → [拍摄] 相机预览 → 快门 → 结果预览     （P4，§5-Q1）
  → [导入] 系统照片选择器 → 选中图像       （§5-Q4）
  → 名片区域检测（显示边界 / 可调整）      （P5，§5-Q2）
  → 确认 → 识别进度                       （P6）
  → 结构化结果确认（人工检查/修改）        （P7）
  → 保存 → 列表顶部出现新名片              （P1）
```

异常分支（规格定义）：

```text
相机权限拒绝 → 提示 + 前往设置 + 相册导入
取消 / 返回   → 不产生数据
识别失败      → 错误提示 + 重试 + 手动录入
字段全空      → 不可保存
```

## 6. 观察结论（Week 1）

1. **外部行为可以用状态机完整描述**：入口 → 来源 → 校正 → 识别 → 确认 → 保存 → 管理 → 导出，
   每一步都有可观察的界面状态与数据结果，因此可以建立确定性的 Reference Test Suite（T01–T20）。
2. **AI 输出不是数据**：OCR/字段抽取是概率性的，必须经「确认 → 可编辑 → 保存」才成为联系人记录；
   原始输出必须保留，用于准确率统计与错误分析（作业 §5、§9）。
3. **「不编造」是硬约束**：字段缺失时宁可留空，也不根据语义补全（作业 §8）。
4. 参考 App 的版本与设备环境未锁定时，任何逐像素/逐文案的「等价」都不可验证；
   本项目把「等价」限定为规格与测试用例定义的行为等价（`docs/spec.md` §1.3）。

### 6.1 已知的观察局限

- 模拟器无真实相机，拍摄与照片库行为不做自动化断言（T04/T05 人工验证）。
- 参考 App 的云端同步、CRM、数字名片等能力不在本切片范围（作业 §15），未做观察。
- 观察记录中的页面号（P1–P12）与 `docs/spec.md` 的页面编号一一对应，便于追溯。
